4. TOOL REGISTRY

File:

src/agent/tool_registry.py

ToolRegistry defines which tools the Agent is allowed to call.

Current tools:

- get_claim
- get_claim_status
- calculate_claim

The registry does not execute arbitrary model-generated Python code.

The model can only select a registered tool name.

This makes tool execution safer and easier to validate.


5. TOOL OBJECT

Each Tool contains:

- name
- description
- params
- func
- writes

Example conceptually:

Tool(
    name="get_claim_status",
    description="Return the current persisted status of a claim.",
    params={"claim_id": str},
    func=get_claim_status,
)

The writes flag identifies whether the tool has side effects.

The current Day 4 tools are read-only.


6. TOOL SCHEMA

Tool.schema() converts the Python tool definition into a structure that can be
shown to an LLM.

Example:

{
    "name": "get_claim_status",
    "description": "...",
    "input_schema": {
        "type": "object",
        "properties": {
            "claim_id": {
                "type": "string"
            }
        },
        "required": [
            "claim_id"
        ]
    }
}

This is useful for future LLM function/tool calling.


7. DISPATCHER

File:

src/agent/dispatcher.py

Dispatcher safely executes one tool call.

Flow:

Agent/model
    |
    | tool name + arguments
    v
Dispatcher
    |
    +--> find tool
    |
    +--> parse arguments
    |
    +--> validate arguments
    |
    +--> execute tool
    |
    v
JSON observation

or:

Error: ...


8. WHY DISPATCHER RETURNS ERROR STRINGS

Example errors tested during Day 4:

Unknown tool:

Error: unknown tool 'delete_all' ...

Wrong argument type:

Error: argument 'claim_id' must be str, got int

Missing claim:

Error: Claim not found: CLM-999

These errors do not crash the program.

A future Agent loop can receive the Error string as an observation and decide
what to do next.


9. SAFE TOOL EXECUTION

The Dispatcher does not use:

eval()

to execute model output.

The model cannot directly run arbitrary Python code.

Instead:

tool_name
    |
    v
registry.get(tool_name)
    |
    v
registered function

This limits execution to known tools.


10. EXACT TYPE VALIDATION

The project intentionally uses exact type checking in important places.

Example:

type(value) is int

instead of:

isinstance(value, int)

Why?

Because Python treats bool as a subclass of int:

isinstance(True, int) == True

But:

True

is not a valid token count.

Therefore exact type checking prevents invalid usage statistics.

ESCALATED

NEED_MORE_INFO

NO_ANSWER


13. NO_ANSWER VS NEED_MORE_INFO

This distinction is very important.

NO_ANSWER:

The Agent does not have enough policy evidence to safely answer.

Example:

The required policy document/version is missing.

NO_ANSWER is an Agent response.

It should not be persisted as ClaimStatus.


NEED_MORE_INFO:

The policy is available, but information about the claim is missing.

Example:

A receipt is required but the employee did not provide it.

NEED_MORE_INFO can be a workflow status.


Simple rule:

missing policy evidence
    ->
NO_ANSWER

missing claim information
    ->
NEED_MORE_INFO


14. SCHEMA VALIDATION

Function:

validate_agent_output()

Its job is only to validate the interface.

It checks:

- output is a dictionary;
- required fields exist;
- answer is a string;
- decision is allowed;
- evidence_refs is a list;
- references are non-empty strings;
- usage exists;
- usage fields exist;
- usage values are non-negative integers.

It does NOT decide whether the Agent answer is correct.


15. VALID FORMAT DOES NOT MEAN CORRECT ANSWER

Example:

{
    "decision": "APPROVED"
}

may be structurally valid.

However, if expected decision is:

ESCALATED

then the Agent is still wrong.

Therefore:

schema validation != evaluation

18. DECISION CORRECTNESS

Formula:

actual_decision == expected_decision

Example:

Expected:

ESCALATED

Actual:

ESCALATED

Result:

True


Example:

Expected:

ESCALATED

Actual:

APPROVED

Result:

False


19. CORRECT REFUSAL

Correct Refusal is evaluated only on cases whose expected decision is:

NO_ANSWER

Example:

Expected:

NO_ANSWER

Actual:

NO_ANSWER

Correct Refusal:

True


Example:

Expected:

NO_ANSWER

Actual:

APPROVED

Correct Refusal:

False


For a normal answerable case:

Expected:

ESCALATED

Correct Refusal:

None

None means:

not applicable.

It does not mean False.


20. EVIDENCE COVERAGE

Evidence Coverage measures how much expected policy evidence appears in the
Agent output.

Formula:

matched expected evidence
-------------------------
total expected evidence


Example:

Expected:

DOC003@v1.0
DOC007@v1.0

Agent:

DOC003@v1.0

Matched:

1

Expected:

2

Evidence Coverage:

1 / 2 = 0.5 = 50%


21. WHY SETS ARE USED FOR EVIDENCE

Suppose the Agent outputs:

DOC003@v1.0
DOC003@v1.0
DOC003@v1.0

Expected:

DOC003@v1.0
DOC007@v1.0

Repeating DOC003 must not increase coverage.

Therefore the evaluator converts references into sets.

Coverage remains:

1 / 2 = 50%


22. EXTRA EVIDENCE

Example:

Expected:

DOC003@v1.0

Agent:

DOC003@v1.0
DOC004@v1.0

Current Evidence Coverage:

100%

because all expected evidence is present.

However, this metric does not penalize extra irrelevant evidence.

This is one limitation of the current coverage metric.


23. NO EXPECTED EVIDENCE

If:

expected_refs = []

then:

evidence_coverage = None

Why not 100%?

Because there is nothing to evaluate.

Giving 100% to empty cases would artificially increase the average coverage.


24. EVIDENCE COVERAGE IS NOT FAITHFULNESS

This is one of the most important Day 4 concepts.

Evidence Coverage asks:

"Did the Agent include the expected references?"

Faithfulness asks:

"Are the statements in the generated answer actually supported by those
references?"

Example:

Agent cites:

DOC003@v1.0

but writes a hotel limit that does not exist in DOC003.

Evidence Coverage may still be 100%.

Faithfulness should fail.

Therefore:

Evidence Coverage != Faithfulness

28. CORRECT REFUSAL RATE

Formula:

correct NO_ANSWER decisions
---------------------------
expected NO_ANSWER cases

Example only:

3 correct refusals
4 no-answer cases

Correct Refusal Rate:

3 / 4 = 75%

Only expected NO_ANSWER cases are included in this denominator.


29. AVERAGE EVIDENCE COVERAGE

Suppose:

Case A = 0.5
Case B = 1.0

Average:

(0.5 + 1.0) / 2
=
0.75

Cases with:

evidence_coverage = None

are excluded.


30. TOKEN USAGE METRICS

The evaluation contract expects:

calls

Number of LLM calls used during the case.

prompt_tokens

Total input tokens across the case.

completion_tokens

Total generated tokens across the case.

max_prompt

Largest single prompt during the case.


Aggregate total:

total_tokens
=
total_prompt_tokens
+
total_completion_tokens


Average:

average_tokens_per_case
=
total_tokens
/
total_cases


Maximum prompt:

max_prompt_tokens
=
max(max_prompt across cases)


31. WHY TOKEN USAGE MATTERS

Token usage helps measure:

- Agent efficiency;
- Agent-loop complexity;
- prompt growth;
- context size;
- approximate future cost;
- whether unnecessary repeated LLM calls occur.

Real monetary cost should only be calculated after the final model and pricing
are known.

38. IMPORTANT DEFENSE QUESTIONS

Question:

Why did you create an evaluation contract?

Answer:

To separate the Agent implementation from the evaluation layer. As long as the
Agent exposes the agreed output structure, Member 1 can evaluate it without
depending on the internal Agent implementation.


Question:

Why is NO_ANSWER different from NEED_MORE_INFO?

Answer:

NO_ANSWER means policy evidence is insufficient. NEED_MORE_INFO means policy
exists but claim information is missing.


Question:

Why is Correct Refusal None for a normal question?

Answer:

Because Correct Refusal only applies to expected NO_ANSWER cases. A normal
answerable case should not affect the refusal-rate denominator.


Question:

Why is Evidence Coverage not Faithfulness?

Answer:

Coverage checks whether expected references are present. Faithfulness checks
whether the generated statements are actually supported by those references.


Question:

Why do you use synthetic Agent outputs?

Answer:

Only to unit-test metric formulas and validation logic. They are not reported
as final system performance.


Question:

Why do you report retrieval metrics separately from Agent metrics?

Answer:

Good retrieval does not guarantee good Agent reasoning. Retrieval and final
Agent behavior measure different layers of the system.
