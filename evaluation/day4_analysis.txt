4. ToolRegistry
---------------

File:

src/agent/tool_registry.py

ToolRegistry định nghĩa những tool mà Agent được phép gọi.

Các tool hiện tại:

- get_claim
- get_claim_status
- calculate_claim

Registry không thực thi arbitrary model-generated Python code.

Model chỉ có thể chọn tool đã được đăng ký.

Điều này giúp tool execution an toàn hơn và dễ validate hơn.


5. Tool object
--------------

Mỗi Tool chứa:

- name
- description
- params
- func
- writes

Ví dụ về mặt ý tưởng:

Tool(
    name="get_claim_status",
    description="Return the current persisted status of a claim.",
    params={"claim_id": str},
    func=get_claim_status,
)

Ý nghĩa:

name
- tên tool mà Agent sử dụng.

description
- mô tả chức năng của tool.

params
- arguments và kiểu dữ liệu yêu cầu.

func
- Python function thực tế được gọi.

writes
- cho biết tool có side effect hay không.

Các tool hiện tại trong Day 4 đều là read-only.


6. Tool schema
--------------

Tool.schema() chuyển Python tool definition thành schema có thể cung cấp cho
LLM.

Ví dụ:

{
    "name": "get_claim_status",
    "description": "...",
    "input_schema": {
        "type": "object",
        "properties": {
            "claim_id": {
                "type": "string"
            }
        },
        "required": [
            "claim_id"
        ]
    }
}

Schema giúp model biết:

- tool nào tồn tại;
- tool làm gì;
- cần argument nào;
- argument có kiểu dữ liệu gì.

Điều này hữu ích cho future LLM function/tool calling.

8. Vì sao Dispatcher trả về Error string?
-----------------------------------------

Một số lỗi đã được kiểm tra trong Day 4:

Unknown tool:

Error: unknown tool 'delete_all' ...

Wrong argument type:

Error: argument 'claim_id' must be str, got int

Missing claim:

Error: Claim not found: CLM-999

Các lỗi này không làm chương trình crash.

Future Agent loop có thể nhận Error string như một observation rồi quyết định
bước tiếp theo.


9. Safe tool execution
----------------------

Dispatcher không sử dụng:

eval()

để chạy model output.

Model không thể trực tiếp thực thi arbitrary Python code.

Thay vào đó:

tool_name
    |
    v
registry.get(tool_name)
    |
    v
registered function

Điều này giới hạn việc thực thi chỉ trong các tool đã được đăng ký.


10. Exact type validation
-------------------------

Project sử dụng exact type checking ở những vị trí quan trọng.

Ví dụ:

type(value) is int

thay vì:

isinstance(value, int)

Lý do:

Python xem bool là subclass của int:

isinstance(True, int) == True

Nhưng:

True

không phải token count hợp lệ.

Vì vậy exact type checking giúp tránh nhận nhầm boolean thành integer usage
statistics.

13. NO_ANSWER và NEED_MORE_INFO
-------------------------------

Đây là điểm rất quan trọng.

NO_ANSWER nghĩa là:

Agent không có đủ policy evidence để trả lời an toàn.

Ví dụ:

Required policy document/version không tồn tại trong corpus.

NO_ANSWER là Agent response.

Nó không phải persisted ClaimStatus.


NEED_MORE_INFO nghĩa là:

Policy đã có, nhưng claim thiếu thông tin cần thiết.

Ví dụ:

Policy yêu cầu receipt nhưng employee chưa cung cấp receipt.

NEED_MORE_INFO có thể là workflow status.


Quy tắc nhớ nhanh:

missing policy evidence
    ->
NO_ANSWER

missing claim information
    ->
NEED_MORE_INFO


14. Schema validation
---------------------

Function:

validate_agent_output()

Nhiệm vụ chỉ là kiểm tra interface.

Nó kiểm tra:

- output có phải dictionary không;
- các required fields có tồn tại không;
- answer có phải string không;
- decision có nằm trong valid decisions không;
- evidence_refs có phải list không;
- mỗi evidence reference có phải non-empty string không;
- usage có tồn tại không;
- required usage fields có tồn tại không;
- usage values có phải non-negative integer không.

Nó KHÔNG đánh giá Agent trả lời đúng hay sai.


15. Valid format không có nghĩa là Correct answer
--------------------------------------------------

Vì vậy:

schema validation != evaluation

18. Decision Correctness
------------------------

Công thức:

actual_decision == expected_decision

Ví dụ:

Expected:

ESCALATED

Actual:

ESCALATED

Result:

True


Ví dụ sai:

Expected:

ESCALATED

Actual:

APPROVED

Result:

False


19. Correct Refusal
-------------------

Correct Refusal chỉ được đánh giá khi expected decision là:

NO_ANSWER

Ví dụ:

Expected:

NO_ANSWER

Actual:

NO_ANSWER

Correct Refusal:

True


Ví dụ:

Expected:

NO_ANSWER

Actual:

APPROVED

Correct Refusal:

False


Với một answerable case bình thường:

Expected:

ESCALATED

Correct Refusal:

None

None nghĩa là:

metric này không áp dụng cho case đó.

None không có nghĩa là False.


20. Evidence Coverage
---------------------

Evidence Coverage đo mức độ Agent output chứa đủ expected policy evidence.

Công thức:

matched expected evidence
-------------------------
total expected evidence

Ví dụ:

Expected:

DOC003@v1.0
DOC007@v1.0

Agent:

DOC003@v1.0

Matched:

1

Total expected:

2

Evidence Coverage:

1 / 2 = 0.5 = 50%


21. Vì sao dùng set cho evidence?
---------------------------------

Giả sử Agent output:

DOC003@v1.0
DOC003@v1.0
DOC003@v1.0

Expected:

DOC003@v1.0
DOC007@v1.0

Việc lặp DOC003 không được làm tăng score.

Do đó evaluator chuyển references thành set.

Coverage vẫn là:

1 / 2 = 50%


22. Extra evidence
------------------

Ví dụ:

Expected:

DOC003@v1.0

Agent:

DOC003@v1.0
DOC004@v1.0

Current Evidence Coverage:

100%

vì toàn bộ expected evidence đều đã xuất hiện.

Tuy nhiên metric này không penalize extra irrelevant evidence.

Đây là một limitation của current Evidence Coverage.


23. Không có expected evidence
------------------------------

Nếu:

expected_refs = []

thì:

evidence_coverage = None

Không trả:

1.0

Lý do:

Không có evidence nào thực sự cần đánh giá.

Nếu cho 100% ở các empty cases thì Average Evidence Coverage có thể bị tăng
một cách không hợp lý.


24. Evidence Coverage không phải Faithfulness
---------------------------------------------

Đây là một trong những khái niệm quan trọng nhất của Day 4.

Evidence Coverage hỏi:

"Agent có đưa ra các expected policy references hay không?"

Faithfulness hỏi:

"Các phát biểu trong câu trả lời của Agent có thực sự được evidence hỗ trợ
hay không?"

Ví dụ:

Agent cite:

DOC003@v1.0

nhưng Agent viết một hotel limit không tồn tại trong DOC003.

Khi đó:

Evidence Coverage vẫn có thể = 100%

nhưng:

Faithfulness phải FAIL.

Do đó:

Evidence Coverage != Faithfulness

28. Correct Refusal Rate
------------------------

Công thức:

correct NO_ANSWER decisions
---------------------------
expected NO_ANSWER cases

Ví dụ minh họa:

3 correct refusals
4 no-answer cases

Correct Refusal Rate:

3 / 4 = 75%

Chỉ các expected NO_ANSWER cases mới được đưa vào denominator.


29. Average Evidence Coverage
-----------------------------

Ví dụ:

Case A = 0.5
Case B = 1.0

Average:

(0.5 + 1.0) / 2
=
0.75

Các case có:

evidence_coverage = None

sẽ bị loại khỏi denominator.


30. Token Usage Metrics
-----------------------

Evaluation contract yêu cầu:

calls

Số lần LLM được gọi trong một case.


prompt_tokens

Tổng số input tokens của cả case.


completion_tokens

Tổng số tokens do model generate trong cả case.


max_prompt

Prompt lớn nhất trong một case.


Aggregate total:

total_tokens
=
total_prompt_tokens
+
total_completion_tokens


Average:

average_tokens_per_case
=
total_tokens
/
total_cases


Maximum prompt:

max_prompt_tokens
=
max(max_prompt across cases)

36. Future Faithfulness evaluation
----------------------------------

Khi có real Agent-generated answers, Member 1 có thể thêm Faithfulness.

Một phương pháp có thể là:

1. Đọc Agent answer.
2. Xác định factual policy claims.
3. Match từng claim với cited evidence.
4. Kiểm tra evidence có thực sự support claim đó không.
5. Tính supported claims / total factual claims.

Faithfulness phải được giữ riêng với Evidence Coverage.

38. Các câu hỏi bảo vệ quan trọng
---------------------------------

Câu hỏi:

Why did you create an evaluation contract?

Trả lời:

Evaluation contract giúp tách Agent implementation khỏi evaluation layer.

Chỉ cần Agent expose đúng agreed output structure thì Member 1 có thể đánh giá
Agent mà không cần phụ thuộc vào implementation nội bộ của Agent.


Câu hỏi:

Why is NO_ANSWER different from NEED_MORE_INFO?

Trả lời:

NO_ANSWER nghĩa là thiếu policy evidence.

NEED_MORE_INFO nghĩa là policy đã có nhưng claim thiếu required information.


Câu hỏi:

Why is Correct Refusal None for a normal question?

Trả lời:

Vì Correct Refusal chỉ áp dụng với expected NO_ANSWER cases.

Normal answerable cases không nên ảnh hưởng denominator của refusal rate.


Câu hỏi:

Why is Evidence Coverage not Faithfulness?

Trả lời:

Coverage kiểm tra expected references có xuất hiện hay không.

Faithfulness kiểm tra các generated statements có thực sự được references hỗ
trợ hay không.


Câu hỏi:

Why do you use synthetic Agent outputs?

Trả lời:

Chỉ để unit-test metric formulas và validation logic.

Synthetic outputs không được dùng làm final system performance.


Câu hỏi:

Why do you report retrieval metrics separately from Agent metrics?

Trả lời:

Good retrieval không đảm bảo good Agent reasoning.

Retriever có thể đưa đúng evidence nhưng Agent vẫn có thể decision sai hoặc tạo
unsupported statements.
